# LittleSprouts — Teacher & Staff Profile

## Objective

Implement a complete Teacher / Staff profile and management feature.

A teacher is not just a user account.

The system must maintain a complete professional profile containing:

* Personal information
* Contact information
* Emergency contact
* Employment information
* Qualifications
* Education
* Certifications
* Skills
* Experience
* Languages
* Childcare specialties
* Classroom assignments
* Work schedule
* Availability
* Professional development
* Documents
* Training
* Permissions
* Status
* Performance / observations
* Teacher preferences

Do NOT put all information into one `Teacher` table.

Separate authentication, person information, employment, skills, qualifications, assignments, schedules, certifications and documents.

# 32. Privacy and Security

Teacher information is sensitive.

Apply role-based access.

A normal teacher should NOT automatically see:

- Another teacher's personal address
- Emergency contact
- Salary/pay information
- Background check details
- Private HR documents
- Performance information

Director/HR/Admin access should be controlled separately.

---

# 33. Audit

Track important changes:

- Certification added
- Certification changed
- Certification verified
- Employment status changed
- Classroom assignment changed
- Role changed
- Sensitive profile information changed
- Document uploaded
- Document deleted
- Background check updated

Include:

- ChangedBy
- ChangedAt
- OldValue where appropriate
- NewValue where appropriate

Do not log sensitive values unnecessarily.

---

# 34. Multi-Tenant Requirement

LittleSprouts is a multi-tenant SaaS.

Every teacher/staff record must belong to the correct organization/tenant.

A user from Daycare A must never access staff information from Daycare B.

Tenant isolation must be enforced in the application/data layer, not only by hiding records in the UI.

Reuse the existing tenant architecture.

# 39. Important Architecture Rule

Before implementing:

1. Inspect the existing project.
2. Reuse the existing User/Identity model.
3. Reuse existing Tenant/Organization.
4. Reuse existing Branch.
5. Reuse existing Classroom.
6. Reuse existing Document/File storage.
7. Reuse existing Audit infrastructure.
8. Reuse existing authorization.
9. Do not create duplicate infrastructure.
10. Follow the existing project's naming and architectural conventions.

Do not rewrite unrelated functionality.

---

# 40. Acceptance Criteria

The feature is complete when:

- A teacher can be created.
- Teacher profile can be saved as a draft.
- Teacher profile can be resumed.
- Employment information can be recorded.
- Multiple qualifications can be recorded.
- Multiple certifications can be recorded.
- Certification expiration can be tracked.
- Multiple skills can be assigned.
- Skill levels can be recorded.
- Multiple languages can be recorded.
- Experience can be recorded.
- Classroom assignments can be maintained historically.
- Teacher schedules can be recorded.
- Availability can be recorded.
- Training can be recorded.
- Documents can be uploaded/referenced.
- Background checks can be tracked where applicable.
- Teacher profile can be activated/deactivated.
- Director can search teachers by skill.
- Director can search teachers by language.
- Director can identify expiring certifications.
- Director can identify teachers by availability.
- Tenant isolation is enforced.
- Sensitive information is protected.
- Important changes are audited.
- Existing application functionality continues to work.

---

# Final Product Principle

The LittleSprouts Teacher profile should answer five questions:

1. **Who is this teacher?**
2. **What qualifications and certifications do they have?**
3. **What are they good at?**
4. **Where and when can they work?**
5. **How can LittleSprouts help them create better experiences for children?**

The system should collect comprehensive information without making the teacher onboarding experience feel like a giant form.

Use progressive completion and a multi-step wizard.
