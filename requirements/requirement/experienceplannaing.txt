# Experience Planning

## EnjoyEveryday — Functional & Technical Requirement

## 1. Objective

Implement the **Experience Planning** capability for EnjoyEveryday.

Experience Planning allows daycare management and teachers to decide:

* What Experience will happen
* Which Class will experience it
* When it will happen
* Which Teacher will facilitate it
* Which Children are expected to participate
* What preparation is required
* Whether the plan is ready for execution

Experience Planning must connect the existing:

* Experience Library
* Experience Studio
* Class
* Teacher
* Child
* Enrollment
* Child Journey
* Harvest & Insight

Do not recreate any of these existing domains.

The implementation must integrate with the current application architecture and UI.

---

# 2. Product Concept

The system has three different concepts.

### Experience

A reusable definition.

Example:

```text
Rainbow Builders
```

It describes:

* Purpose
* Age group
* Development areas
* Materials
* Instructions
* Duration
* Environment
* Safety

---

### Experience Plan

A planned occurrence.

Example:

```text
Rainbow Builders

Bluebirds Classroom
October 5
10:00 AM
Teacher: Priya
```

---

### Experience Session

The actual execution.

Example:

```text
Rainbow Builders

Actually started:
10:07 AM

Actually completed:
10:39 AM

16 children expected
14 participated
1 partially participated
1 absent
```

Therefore:

```text
Experience
     ↓
Experience Plan
     ↓
Experience Session
```

Experience Planning is responsible for the middle layer.

# 17. Children in Planning

Do not permanently copy children into ExperiencePlan.

The expected children should be derived from the Classroom's active enrollment.

Example:

```text
Bluebirds

Active Enrollment:
16 children
```

Therefore the plan knows:

```text
Classroom = Bluebirds
```

and the application can determine:

```text
Expected Children = current active enrollment
```

This prevents stale child information.

---

# 18. Important Rule — Planned vs Actual

Planning and execution must remain separate.

Planning says:

> These children are expected to participate.

Execution says:

> These children actually participated.

Therefore:

```text
ExperiencePlan
      ↓
Expected Classroom Children

ExperienceSession
      ↓
Actual ExperienceParticipation
```

Do not create final participation records simply because a plan was created.

# 25. Start Experience

The planning implementation should provide the handoff:

```text
Experience Plan
      ↓
Start Experience
      ↓
Experience Session
```

When the teacher clicks:

```text
Start Experience
```

the application should:

1. Validate the plan.
2. Validate Classroom.
3. Validate Teacher.
4. Load current children.
5. Create or activate ExperienceSession.
6. Copy the required planning context.
7. Record ActualStartTime.
8. Change plan/session state appropriately.

Do not copy unnecessary master data.

# 33. Multi-Tenant Security

Every query and command must enforce Tenant isolation.

Never trust a TenantId supplied by the UI.

The authenticated tenant context must determine the tenant.

Validate all relationships:

```text
Experience → Tenant
Classroom → Tenant
Teacher → Tenant
ExperiencePlan → Tenant
```

A user must never be able to create a plan by supplying IDs from another tenant.

# 47. Do Not Do These Things

Do NOT:

* Create a second Child entity.
* Create a second Teacher entity.
* Create a second Classroom entity.
* Create a second Child Journey.
* Create a second Harvest system.
* Store children as JSON inside ExperiencePlan.
* Store teacher information as duplicated text.
* Store classroom information as duplicated text.
* Automatically create Journey entries for every planned Experience.
* Treat a Plan as an actual completed Experience.
* Allow a completed Session to be silently changed.
* Redesign existing screens unnecessarily.
* Introduce a new architectural pattern.

# 48. Definition of Done

Experience Planning is complete when:

### Planning

* Experience can be selected.
* Classroom can be selected.
* Teacher can be selected.
* Date can be selected.
* Time can be selected.
* Preparation can be reviewed.
* Plan can be saved.
* Plan can be confirmed.

### Validation

* Tenant isolation works.
* Classroom conflicts are detected.
* Teacher conflicts are detected.
* Invalid dates/times are rejected.
* Inactive Experience cannot be planned.
* Inactive Classroom cannot be planned.
* Inactive Teacher cannot be assigned.

### Planning Management

* Plans can be viewed.
* Plans can be edited.
* Plans can be rescheduled.
* Plans can be cancelled.
* Plans have valid lifecycle states.
* Audit information is captured.

### Teacher

* Teacher can see today's Experiences.
* Teacher sees correct Classroom.
* Teacher sees correct Experience.
* Teacher sees expected children.
* Teacher can start the Experience.

### Execution Handoff

* Start creates/activates ExperienceSession.
* Session references ExperiencePlan.
* Session references Experience.
* Session references Classroom.
* Session references Teacher.
* Actual execution is separated from planning.

### Child Journey

* Existing Child Journey can be launched from the Session.
* Journey Entry retains Experience context.

### Harvest

* Existing Harvest receives completed Experience evidence.
* No duplicate Harvest implementation is introduced.

# 49. Final Product Principle

Experience Planning should make the EnjoyEveryday loop feel like this:

```text
DISCOVER
   ↓
CHOOSE AN EXPERIENCE
   ↓
PLAN IT
   ↓
PREPARE THE CLASSROOM
   ↓
DO IT WITH CHILDREN
   ↓
CAPTURE ONE LITTLE MOMENT
   ↓
CHILD JOURNEY GROWS
   ↓
HARVEST
   ↓
INSIGHT
```

The teacher should never feel that they are moving between disconnected modules.

They should feel:

> **"I planned something meaningful for my children, did it with them, captured what mattered, and their story continued."**

The implementation priority is:

```text
1. ExperiencePlan
2. Planning Wizard
3. Planning Validation
4. Planning Calendar/List
5. Today's Experiences
6. ExperienceSession handoff
7. Child/Teacher/Class context
8. Existing Child Journey integration
9. Existing Harvest integration
10. Audit + security + concurrency
```

Do not expand beyond this scope until this complete flow works end-to-end.
