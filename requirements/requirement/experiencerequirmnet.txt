# Experience Integration Requirements

## EnjoyEveryday

## 1. Purpose

The existing EnjoyEveryday system contains:

* Experience Library
* Experience Studio
* Experience Planning
* Harvest & Insight
* Child
* Child Journey
* Class
* Teacher

The goal of this requirement is to connect these existing areas through a single Experience lifecycle.

The system should treat **Experience as the central learning/activity concept**.

Do not redesign the existing UI unless required for integration.

The implementation should primarily add:

* Domain relationships
* Data model
* Business rules
* Application services
* APIs
* Persistence
* Navigation/context
* Validation
* Audit
* Child Journey integration
* Harvest & Insight integration

---

# 2. Core Concept

The system must distinguish between:

### Experience

A reusable definition of something teachers can do with children.

Example:

> Rainbow Builders

It describes:

* What the experience is
* Intended age group
* Purpose
* Development areas
* Materials
* Instructions
* Expected duration
* Environment
* Safety considerations

An Experience does NOT represent a specific occurrence.

---

### Experience Session

An actual occurrence of an Experience.

Example:

> Rainbow Builders conducted in Bluebirds classroom on October 4, 2026.

The Experience Session records:

* When it happened
* Where it happened
* Which teacher facilitated it
* Which children participated
* What actually happened

Therefore:

**Experience = reusable definition**

**Experience Session = actual execution**

# 11. Class

An Experience Session belongs to one Classroom.

Relationship:

```text
Classroom
     │
     └── ExperienceSession
```

A Classroom can have many Experience Sessions.

An Experience Session belongs to exactly one Classroom.

The Classroom domain remains the source of truth for:

* Classroom
* Branch
* Capacity
* Classroom teachers
* Classroom status

Do not duplicate Classroom master information in Experience.

# 13. Important Child Relationship

The system must NOT simply store:

```text
Experience → Child
```

because this loses important historical context.

Instead:

```text
Experience
    ↓
ExperienceSession
    ↓
ExperienceParticipation
    ↓
Child
```

This allows the system to answer:

* Which experience?
* When?
* Which classroom?
* Which teacher?
* Which child?
* Did the child participate?
* How did the child participate?
* What did the teacher observe?

# 15. Teacher Journey Capture

After completing an Experience Session, the teacher should be able to capture a small observation for one or more children.

The teacher flow should be extremely simple:

```text
Experience Completed
        ↓
Children Participated
        ↓
Select Child
        ↓
What happened?
        ↓
What did you notice?
        ↓
Save
```

Example:

> Maya worked with two other children and helped them build the bridge.

This creates a Child Journey Entry.

The teacher should NOT be required to complete a large assessment form.

# 23. Business Rules

## Rule 1 — Tenant Isolation

Every Experience-related entity must contain TenantId where required.

A tenant must never see another tenant's:

* Experiences
* Sessions
* Children
* Teachers
* Journey entries
* Insights
* Media

---

## Rule 2 — Experience Cannot Be Deleted If Used

If an Experience has been used in an Experience Session:

Do not physically delete it.

Set:

```text
Status = Archived
```

Historical sessions must remain valid.

---

## Rule 3 — Historical Integrity

Changing an Experience must not change historical sessions.

Use Experience versioning.

Example:

```text
Rainbow Builders v1
     ↓
Session on Oct 1

Rainbow Builders v2
     ↓
Session on Oct 10
```

Both historical sessions must remain accurate.

---

## Rule 4 — Completed Sessions

Once an Experience Session is completed:

* Do not silently change classroom
* Do not silently change date
* Do not silently change teacher
* Do not silently change participating children

Changes must follow existing correction/audit rules.

---

## Rule 5 — Child Journey Authority

Experience provides context.

Child Journey provides the child's developmental story.

Therefore:

```text
Experience ≠ Assessment
```

Experience should never automatically assign a developmental score to a child.

---

## Rule 6 — Teacher Authority

AI may suggest:

* Experience recommendations
* Development areas
* Observation summaries
* Patterns
* Possible next experiences

AI must not:

* Invent observations
* Invent child behavior
* Create false evidence
* Diagnose children
* Automatically publish parent content
* Override teacher observations

# 31. Experience Planning → Session

The key transition is:

```text
Experience Plan
       ↓
Start
       ↓
Experience Session
```

When the teacher starts a planned Experience:

1. Create or activate Experience Session.
2. Load Classroom.
3. Load assigned Teacher(s).
4. Load eligible Children.
5. Create ExperienceParticipation records as appropriate.
6. Allow teacher to record participation.
7. Allow observations.
8. Allow Little Moments.
9. Allow evidence.
10. Complete the Session.

---

# 32. Eligibility

When planning an Experience for a Classroom, validate:

* Classroom belongs to the current Tenant.
* Classroom is active.
* Teacher belongs to the current Tenant.
* Teacher is eligible to work with the Classroom according to existing assignment rules.
* Experience belongs to the current Tenant.
* Experience is Published.
* Experience age range is compatible with the Classroom/children where required.

Do not silently block legitimate mixed-age scenarios if the existing business rules permit them.

# 37. Important Architectural Principle

Use the following separation:

```text
EXPERIENCE
"What can we do?"

EXPERIENCE PLAN
"What are we going to do?"

EXPERIENCE SESSION
"What did we actually do?"

PARTICIPATION
"Who took part?"

CHILD JOURNEY
"What did we notice about this child?"

LITTLE MOMENT
"What beautiful/meaningful moment happened?"

HARVEST
"What evidence have we collected?"

INSIGHT
"What patterns are emerging?"
```

This separation is the foundation of the integration.

# 42. Acceptance Criteria

The implementation is complete when:

* An Experience can be created and published.
* A published Experience can be planned.
* A plan can be associated with a Classroom.
* A plan can be associated with one or more Teachers.
* A planned Experience can become an Experience Session.
* A Session can contain participating Children.
* Participation status can be recorded.
* A Teacher can complete an Experience Session.
* A Teacher can capture a Child observation from the Session.
* The observation creates a Child Journey Entry.
* The Journey Entry references the actual Experience Session.
* Little Moments can reference the Experience Session.
* Existing Media can be attached as evidence.
* Harvest can retrieve Experience Session evidence.
* Insight can use harvested evidence.
* Historical Sessions remain correct when an Experience is later changed.
* Tenant isolation is enforced.
* Existing authorization rules are respected.
* Existing audit mechanisms are used.
* Existing UI design is preserved.
* No duplicate Experience, Child, Teacher, Classroom, or Journey domain is introduced.

```text
                                                       PARENT STORY
```

## Core principle

**Experience is the center of the Everyday learning loop.**

The system should answer four simple questions:

> **What did we plan?** → Experience Planning
> **What did we do?** → Experience Session
> **Who experienced it?** → Participation
> **What did we learn about the child?** → Child Journey

This creates a connected system instead of separate modules.
