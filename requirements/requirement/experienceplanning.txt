# Experience Planning — End-to-End Integration

## EnjoyEveryday

## 1. Objective

Experience Planning is the bridge between the reusable Experience and the actual everyday classroom execution.

The existing system already has:

* Experience Library
* Experience Studio
* Experience Planning
* Class
* Teacher
* Child
* Child Journey
* Harvest & Insight

Child Journey and Harvest are already implemented.

The next implementation step is to connect **Experience Planning with the complete existing flow**.

Do not redesign existing modules.

Do not recreate Child Journey or Harvest.

The goal is to make Experience Planning orchestrate the actual classroom experience.

---

# 2. Target Flow

The final flow should be:

```text
Experience Library
        ↓
Experience
        ↓
Experience Planning
        ↓
Planned Experience
        ↓
Classroom
        ↓
Teacher
        ↓
Children
        ↓
Today's Experience
        ↓
Start Experience
        ↓
Execute
        ↓
Complete Experience
        ↓
Child Journey
        ↓
Harvest & Insight
```

The key principle is:

> Experience Planning decides what the classroom is going to experience and prepares the context required for execution.

---

# 3. Important Distinction

Do not treat Experience Planning as another copy of Experience.

### Experience

Reusable definition.

Example:

```text
Rainbow Builders
```

### Experience Plan

A scheduled intention.

Example:

```text
Rainbow Builders
Bluebirds
October 4
10:00 AM
Teacher: Priya
```

### Experience Session

The actual classroom occurrence.

Example:

```text
Rainbow Builders
Bluebirds
October 4
10:07 AM – 10:42 AM
Actually conducted by Priya
```

Therefore:

```text
Experience
    ↓
Experience Plan
    ↓
Experience Session
```

---

# 4. Experience Planning Responsibilities

Experience Planning should answer:

* What Experience are we doing?
* When are we doing it?
* Which classroom?
* Which teacher?
* Which children?
* What preparation is required?
* What is the expected duration?
* Is the plan confirmed?
* Has it started?
* Has it been completed?
* What actually happened?

Experience Planning should NOT store:

* Child master information
* Teacher master information
* Classroom master information
* Child Journey information
* Harvest information

Those domains remain the source of truth.

```text

   ↓
Planned
   ↓
Confirmed
   ↓
```

# 11. Planned Children vs Actual Participation

This distinction is important.

Planning answers:

> Who do we expect?

Execution answers:

> Who actually participated?

Therefore do not permanently treat all planned children as participants.

Example:

```text
Plan

Expected:
16 children
```

Actual session:

```text
Participated:
14
Partially participated:
1
Absent:
1
```

Actual participation belongs to the Experience Session.

# 21. Complete Experience

When the teacher finishes:

```text
[Complete Experience]
```

the system should:

1. Validate the session.
2. Record ActualEndTime.
3. Update session status to Completed.
4. Finalize participation.
5. Preserve Journey entries.
6. Preserve Little Moments.
7. Preserve evidence.
8. Make the completed session available to Harvest.

Do not automatically create Journey entries for children without observations.

---

# 22. What Happens After Completion

The completed Experience Session becomes historical evidence.

```text
Completed Session
       │
       ├── Participation
       │
       ├── Child Journey
       │
       ├── Little Moments
       │
       ├── Media/Evidence
       │
       └── Harvest
```

Harvest should use the existing implementation.

Experience Planning should not duplicate Harvest logic.

# 28. Planning Validation

Before confirming a plan, validate:

### Experience

* Experience exists.
* Experience belongs to Tenant.
* Experience is Published.

### Classroom

* Classroom exists.
* Classroom belongs to Tenant.
* Classroom is active.

### Teacher

* Teacher belongs to Tenant.
* Teacher is active.
* Teacher is assigned/eligible for the Classroom according to existing rules.

### Date/Time

* Valid date.
* Valid start/end time.
* End time is after start time.

### Conflicts

Check for:

* Teacher already scheduled.
* Classroom already scheduled.
* Existing conflicting Experience Plan.

Use the existing scheduling rules if available.

---

# 29. Rescheduling

Allow a planned Experience to be rescheduled before execution.

Example:

```text
Oct 4
10:00 AM
       ↓
Oct 5
11:00 AM
```

Keep an audit record of the change.

Do not modify a completed Session when rescheduling a future plan.

---

# 30. Cancellation

A planned Experience can be cancelled.

Example:

```text
Status:
Cancelled

Reason:
Outdoor area unavailable
```

A cancelled plan must not create a completed Experience Session.

If a Session has already started, cancellation should follow separate existing operational rules.

---

# 31. Missed Experience

If an Experience was planned but never started:

```text
Planned
   ↓
Missed
```

or use the existing cancellation/closure approach.

Do not create false execution records.

This is important for accurate Harvest and Insight.

---

# 32. Repeating Experiences

If the existing Experience Planning supports recurring planning, keep the reusable Experience separate from each occurrence.

Example:

```text
Experience:
Story Circle

Plans:

Oct 1
Oct 2
Oct 3
Oct 4
Oct 5
```

Each actual execution must have its own Session.

Never create one Session covering multiple days.

---

# 33. Versioning

If an Experience changes after planning:

```text
Experience v1
        ↓
Existing Plan
```

do not silently change the historical meaning.

At execution time, preserve the Experience version used.

Example:

```text
Rainbow Builders v1
Plan created
        ↓
Rainbow Builders v2 published
        ↓
Old Plan remains associated with v1
```

Use the existing versioning mechanism if already implemented.

---

### Lead Teacher

* Execute
* Capture observations

### Teacher

Can:

* View assigned experiences
* Start where permitted
* Record participation
* Capture observations
* Complete where permitted

---

# 35. Tenant Isolation

Every operation must validate TenantId.

A user must never be able to:

* Plan another tenant's Experience.
* Assign another tenant's Classroom.
* Assign another tenant's Teacher.
* Access another tenant's Children.
* Access another tenant's Sessions.
* Access another tenant's Journey information.

Never trust TenantId supplied by the client.

Resolve tenant context from the authenticated user/session.

# 42. Definition of Done

Experience Planning integration is complete when:

* An Experience can be selected from Experience Library.
* An Experience can be planned.
* A Classroom can be assigned.
* A Teacher can be assigned.
* Expected Children can be derived from Classroom enrollment.
* Planning conflicts are detected.
* A Plan can be confirmed.
* Today's Experiences can be retrieved.
* Teacher can start an Experience.
* Starting creates an Experience Session.
* Session retains the Plan relationship.
* Session knows Classroom.
* Session knows Teacher.
* Session loads Children.
* Participation can be recorded.
* Existing Child Journey can be invoked from the Session.
* Existing Little Moment functionality can be invoked from the Session.
* Existing Media/Evidence functionality can be invoked from the Session.
* Session can be completed.
* Completed Session appears in Experience history.
* Completed Session appears in Classroom history.
* Completed Session appears in Teacher history.
* Completed Session appears in Child experience history.
* Existing Child Journey contains the Experience context.
* Existing Harvest can consume the completed Session/evidence.
* No duplicate Child Journey or Harvest implementation is created.
* Tenant isolation is enforced.
* Existing permissions are respected.
* Existing audit/concurrency patterns are respected.
* Existing UI design is preserved.

## Product Principle

The teacher should not feel:

> "I am moving between Experience Planning, Child, Teacher, Journey and Harvest."

The teacher should feel:

> **"I planned today's experience, did it with my children, captured what mattered, and their journey grew."**

That is the integration Experience Planning must provide.
