# EXPERIENCE STUDIO — FULL FUNCTIONAL IMPLEMENTATION

## 1. OBJECTIVE

The Experience Studio page already has the desired UI/UX design.

DO NOT redesign the page.

DO NOT change the visual language, layout, spacing, cards, colors, typography, navigation, or overall structure unless required to fix a functional issue.

The goal is to make the existing Experience Studio fully functional and connected to the existing EnjoyEveryday application architecture.

The page should become a real Experience authoring workspace.

The user should be able to:

1. Create an Experience
2. Edit an Experience
3. Save as Draft
4. Add/edit Experience sections
5. Add materials
6. Add teacher guidance
7. Add challenge
8. Add collaboration instructions
9. Add child choice
10. Add creation activity
11. Add magic moment
12. Add accomplishment
13. Add reflection
14. See Experience context
15. Get AI suggestions
16. Apply AI suggestions
17. Preview the Experience
18. Save a new version
19. View previous versions
20. Publish the Experience
21. Send the published Experience to Experience Library
22. Plan the Experience through Experience Planning
23. Preserve audit/history
24. Prevent accidental data loss

The Experience Studio is an authoring tool.

Experience Planning is responsible for scheduling the Experience.

Experience Session is responsible for the actual execution.

Do not mix these responsibilities.

# 7. EXPERIENCE STATUS

Use a clear lifecycle.

Recommended:

Draft
    ↓
Ready
    ↓
Published
    ↓
Archived

Do not allow an invalid state transition.

Draft:
- Editable
- Not normally available for planning

Ready:
- Completed enough to be reviewed
- Can be previewed

Published:
- Available in Experience Library
- Can be selected for Experience Planning

Archived:
- Cannot be newly planned
- Existing historical sessions remain intact

If the current system already has a status model, reuse it.


# 8. SAVE DRAFT

The user must be able to save changes without publishing.

Implement:

[Save Draft]

Behavior:

1. Validate only required fields.
2. Save current state.
3. Preserve all other data.
4. Update UpdatedAt/UpdatedBy.
5. Maintain Version.
6. Show a small success message.

Example:

"Draft saved"

Do not navigate away from Studio after saving.


# 9. AUTO-SAVE

If the existing application architecture supports auto-save, it may be implemented.

Do NOT make auto-save mandatory if it conflicts with the existing architecture.

If auto-save is implemented:

- Save after meaningful changes.
- Avoid excessive API/database calls.
- Show:

"Saving..."
"Saved just now"

Never silently lose changes.

# 16. AI SAFETY / TRUST

AI must follow these rules:

AI can:

- Suggest
- Rewrite
- Expand
- Simplify
- Make playful
- Add child-choice ideas
- Suggest materials
- Suggest teacher questions
- Suggest alternative approaches

AI cannot:

- Invent child observations
- Invent child behavior
- Modify Child Journey automatically
- Create fake participation
- Diagnose children
- Automatically publish an Experience
- Automatically schedule an Experience
- Override teacher decisions

Every AI-generated change must be explicitly accepted.

- Reason
- Confidence
- RequiresApproval

For example:

  "currentContent": "Children choose what they want to protect.",
  "suggestedContent": "Children choose what to protect and which material to test first.",
  "reason": "Adds meaningful choice without making the activity complicated.",
  "confidence": 0.91,
  "requiresApproval": true
}

The exact schema should follow the existing application conventions.

# 56. AI TOOL / AGENT REGISTRATION

If the existing application uses dynamic agents/tools, register the Experience Studio AI capability using that existing mechanism.

    ↓

# 57. REAL TOOL EXECUTION

If the Experience Studio agent has access to tools, the agent must use the actual registered tools.

Examples of potentially useful tools:

- Search Experience Library
- Get Experience
- Get Experience Version
- Search similar Experiences
- Get age guidance
- Get available materials
- Get classroom context

Do not create fake tool results.

If a tool does not exist, do not pretend that it exists.

First inspect the existing tool registry.

Reuse existing tools where possible.

# 59. AI RESPONSE MUST SHOW SOURCE / CONTEXT WHEN APPLICABLE

If an AI recommendation is based on an existing Experience, show a simple explanation.

Example:

"Based on 3 similar Experiences in your library..."

Do not expose internal agent reasoning or chain-of-thought.

Only show a concise user-facing explanation.


# 60. AI FAILURE MUST NOT BREAK STUDIO

The existing Studio must continue working.

AI is an assistant, not a required dependency for basic Experience authoring.

# 65. ACCEPTANCE CRITERIA FOR AI

AI integration is NOT complete if:

- It returns hard-coded suggestions.
- It uses mock services.
- It uses static JSON.
- It only displays sample text.
- The button only opens a dialog.
- The UI directly calls an LLM.
- The AI response is not connected to the actual agent.
- The user cannot apply the suggestion.
- The suggestion automatically changes the database.

AI integration IS complete only when:

UI
 ↓
Existing application AI service
 ↓
Real Google ADK agent
 ↓
Configured model/tools
 ↓
Real response
 ↓
Structured result
 ↓
Teacher approval
 ↓
Experience update
 ↓
Save/version
